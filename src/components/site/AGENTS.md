# Product interactions
- Student referral surfaces read their all-level downline (names, member codes, parent, level, join date and net commission income only) through the own-network RPC, never broader profile reads. Why: students see the same team relationships as Admin without exposing private profile fields or other teams.
- Affiliate Team Tree dialogs keep close controls outside bounded scrolling content and use viewport-sized width. Why: wide/deep teams cannot hide dismissal controls or overflow the page.
- Admin and student Team Trees share desktop-style horizontal parent/child branches at every breakpoint, with compact phone nodes inside a bounded two-axis scrolling canvas and a separate inspector. Why: the requested tree structure stays intact and every branch remains reachable without widening the page.
- Phone Tree canvases share TreeCanvas with react-zoom-pan-pinch for button zoom, pinch and pan; desktop keeps native scrolling. Why: both panels use the same gesture handling and reset behavior.
- Home uses a shared horizontal shelf with responsive widths and accessible previous/next controls; full catalogs keep grids. Why: all saved products remain reachable without multi-row Home sections or changes to admin branding.
- Use ProductSocial for every product card/detail; own-only RLS writes and safe metadata RPCs supply persistent engagement, and shared URLs never contain private resources or meeting links. Why: every product surface shares behavior without exposing participant identities or paid files.- Website banners render through one shared slider whose button rules live in website-banners helpers; links accept only site paths or https. Why: admin-edited slides cannot inject unsafe links and preview matches the live slide.

- Product cards open purchases in the shared PaymentDialog (ManualPayForm body, mounted only while open) and show ProductSocial compact beside the date/price or under the cover; detail pages keep the full social row. Why: buyers pay without leaving the list, and access/payment queries do not run for every card.
- Course and session detail pages share ProductDetailLayout (header, sticky purchase aside, body). Below the desktop breakpoint course details use tabs and a body-portalled fixed price bar, and catalog cards use the CatalogRow layout (course rows link to details). Why: phones/app match the reference while desktop keeps its grid and aside.
- Student data tables add `stack-table` with per-cell `data-label` so phones show labelled cards instead of sideways scrolling; why: wide tables stay readable on small screens.
- Shared page motion observes only newly added content for one-shot intersection entrances, excludes lesson/video/iframe surfaces, and animates outer phone groups rather than nested candidates; CSS interactions respect reduced motion. Why: animations avoid repeated full-page scans, double movement and video-control interference.
- Below the desktop breakpoint the app uses the floating MobileNav dock, MobilePageBar title bars and AppIcons duotone glyphs, styled in the phone/app section of styles.css; session cards share SessionCard. Why: one phone design system keeps every screen consistent while desktop layouts stay untouched.
